# Data model and pipeline

## Where the data comes from

```
data/source/*.xlsx                SAP Customer Checkout report exports, unmodified
        │
        │  tools/etl_sap_export.py          stage 1 — parse the report sheets
        ▼
data/canonical/*.csv              tidy tables + manifest.json with the reconciliation
        │
        │  tools/synthesize_dataset.py      stage 2 — build the network (seeded)
        ▼
db/data/smart.retail-*.csv        master data and facts CAP deploys
        │
        │  tools/generate_ai_outputs.js     stage 3 — run the six engines
        ▼
db/data/smart.retail-<AI>.csv     scenario output
```

### Stage 1 — extraction

The workbooks are report exports, not tables. Every sheet carries five or six lines of run
metadata above the real header, group sheets repeat a parent key only on the first row of each
block, and a trailing `Total` row is mixed in with the data. `etl_sap_export.py` deals with all
three, then writes `manifest.json` so the extraction can be checked against SAP's own totals.

It reconciles exactly:

| Measure | SAP report | Extracted |
|---|---|---|
| Units | 6,452 | 6,452 |
| Gross sales | €10,588.86 | €10,588.86 |
| Net revenue | €9,563.36 | €9,563.36 |
| Hourly rows | — | 4,926 across 179 days |

Which workbook is treated as primary is decided by which one carries more hourly rows, not by the
filename — the filenames in this dataset disagree with the report periods inside them.

### Stage 2 — synthesis

Walldorf (`WDF01`) keeps its exported figures unchanged. Five further stores are generated by
measuring the export's behaviour and replaying it at a different scale:

- **Hour-of-day shares and day-of-week factors** are taken from the real hourly rows.
- **Article mix** follows the real distribution, tilted per store format (food-to-go over-indexes
  in the flagship, drinks in the campus kiosk).
- **Weekend damping** applies to campus formats only — a city-centre store does not empty out on a
  Saturday the way an office-campus store does.
- **Cancellation rates** differ by terminal type, because an unstaffed gate has nobody to resolve a
  misread.
- **Case sizes** mean a fresh line selling half a unit a day still receives a full case, which is
  where most fresh waste actually comes from.

Everything is driven from one seed (`SEED = 20260703`), so the dataset is reproducible.

| Entity | Rows | Source |
|---|---|---|
| `Stores` | 6 | 1 real, 5 synthesized |
| `Articles` | 327 | all from the SAP export |
| `ArticleGroups` | 63 | from the export, enriched with English names, temperature zones, shelf life |
| `HourlySales` | 27,118 | 4,926 real (Walldorf), rest synthesized |
| `Receipts` / `ReceiptItems` | 18,401 / 29,054 | baskets reconstructed from the hourly grain |
| `Cancellations` | ~5,400 | Walldorf totals are the real ones, spread across the days it sold |
| `InventorySnapshots` | 17,640 | 21 days × the moving assortment |
| `ShelfSensorReadings` | 3,738 | vision stockout, ESL price, temperature probes |
| `FootfallReadings` | 9,221 | back-solved from receipts and a conversion rate |

### Stage 3 — scoring

`tools/generate_ai_outputs.js` calls the engines in `srv/lib/engines/` and writes their output.
The running service calls **the same functions** from its `recalculate` action, so the seeded rows
and a live re-run agree by construction rather than by discipline.

## Entity overview

**Operational** (`db/schema.cds`) — `Stores`, `PosSystems`, `Suppliers`, `ArticleGroups`,
`Articles`, `Customers`, `Employees`, `HourlySales`, `Receipts`, `ReceiptItems`, `Cancellations`,
`Returns`, `PaymentFacts`, `InventorySnapshots`, `ShelfSensorReadings`, `FootfallReadings`.

**Scenario output** (`db/ai-schema.cds`) — `DemandForecasts`, `ShrinkAlerts`,
`ReplenishmentTasks`, `MarkdownRecommendations`, `BasketAffinities`, `NextBestOffers`,
`ColdChainAlerts`, `AIInsights`, `ModelMetrics`.

### Conventions

- **Readable keys.** `SA-000042`, `HS-WDF01-000123`. The pipeline regenerates these tables from
  scratch, so stable keys keep the output diffable, and `AIInsights.sourceId` can point back at the
  scenario row that produced an insight.
- **Explicit decimals.** Money and quantities are `Decimal(p,s)`, never `Double`.
- **Criticality is stored, not derived at render time.** Fiori elements colours by an integer
  (`1` red, `2` orange, `3` green), so the engines write it alongside the severity label.
- **Provenance is a first-class field.** `Stores.isReferenceStore` and `Articles.isFromSapExport`
  record what came from SAP rather than leaving it to documentation.

## Engine reference

| Engine | File | Core idea |
|---|---|---|
| Forecast | `forecast.js` | `quantity ≈ level × hourShare(hour) × dayFactor(weekday)`; level is an EWMA over the store's full calendar including zero days |
| Checkout integrity | `shrink.js` | Four independent signals scored 0–100; the strongest names the pattern, value at risk breaks ties |
| Replenishment | `replenishment.js` | `recommended = leadTimeDemand + z·σ/reliability − onHand − onOrder`; urgency from coverage hours |
| Markdown | `markdown.js` | Sweeps candidate depths, keeps the one maximising `recovery − writeOff` under a constant-elasticity response |
| Affinity | `affinity.js` | Support / confidence / lift over reconstructed baskets; flags cross-zone pairs |
| Personalisation | `personalization.js` | Routine (purchase cadence) + discovery (affinity lift), gated on marketing consent |
| Cold chain | `coldchain.js` | Sustained excursions only; severity scales with depth, duration and stock exposed |
| Insight feed | `insights.js` | Ranks every scenario by `impact × confidence`; collapses repeat cabinet alerts to the worst |

## Measuring the forecast honestly

Two decisions matter more than the model itself.

**The level counts zero days.** An article selling on 30 of 179 days has 149 genuine zeros.
Averaging only the days it sold gives the mean of a *selling* day, not the mean of a day — an
earlier version did exactly that and over-predicted by roughly six times.

**The backtest scores the full grid.** Evaluating only rows present in the sales table silently
drops every hour the model predicted demand into and none arrived. Scoring the full
store × article × hour grid with absent slots as true zeros moved the measured store-day WAPE from
a flattering-but-wrong number to the honest 28.8%.

Accuracy is reported as WAPE rather than MAPE because hourly demand is intermittent, and MAPE
divides by actuals of one or two units.
